# Threat model: `keelio-vault` v0

What can go wrong with `keelio-vault`, who can make it go wrong, and what the contract does about it.
Each threat has one status:

- **handled**: the contract stops it, and a linked test asserts that.
- **accepted**: the contract does not stop it in v0. The row gives the worst case in base units.
- **planned**: a named milestone fixes it. Until then it is accepted, with the worst case given.

Every test is cited by its exact `it(...)` name. `tests/keelio-vault-threats.test.ts` fails if a cited
name is not in the cited file, so a renamed test breaks the build instead of leaving a dead claim
here.

## Scope

- `contracts/keelio-vault.clar` (v0) as it stands at this commit, run on the Clarinet simnet only.
- The swap adapter is `ALLOWED-ADAPTER`. On the simnet that is `mock-dex`; a deployment would fix a
  real adapter in its place.
- The price oracle is `ORACLE`, read as BTC/USD. On the simnet that is `mock-oracle`; a deployment
  would fix DIA's `dia-oracle` in its place.
- The adapter tested live is `bitflow-adapter`, in a vault copy that differs only in its deploy
  configuration, run on the simnet with remote mainnet data (`tests/bitflow-adapter.test.ts`).
- Out of scope: the SDK (`packages/sdk`, including the off-chain `checkIntent`) and the MCP server
  (`packages/mcp`). Nothing off-chain counts as handling a threat here.

Amounts are base units: sats for sBTC (`ALLOWED-TOKEN`), and the quote token's own base units for
`QUOTE-TOKEN`.

| T3  | The agent trades at a bad price inside its caps.                                                                                                                   | handled  | The vault refuses a `min-out` below the floor it computes from the fixed `ORACLE`'s BTC/USD price, the tokens' decimals and the owner's `max-slippage-bps` (u125). ## Follow-ups

None of these is fixed here.

- **Owner key recovery (T5):** decided on 16 November 2026: v0 deliberately has no recovery and no guardian. Owners limit the exposure with a short `expires-at`. Revisit before any mainnet deployment.
- **Oracle (T3):** done. `execute-swap` refuses a `min-out` below the oracle floor and a stale price.
- **Oracle in the SDK and MCP (T3):** done. The SDK has a `set-price-bounds` builder, `readVault` reads `get-price-bounds`, and `checkIntent` predicts u119 to u125 and the floor.
- **Oracle deploy check (T3):** done. `pnpm run check-deploy` refuses a `PRICE-SCALE` that is not `10^(8 + sBTC decimals - quote token decimals)` by the tokens' `get-decimals`, and an `ORACLE` whose `get-value` lacks the oracle trait's signature. It cannot read the decimals of the oracle's price, takes them as 8 and says so.
- **Wider oracle checks (T3):** a confidence or deviation band, a second price source, and an sBTC/BTC peg check, for residuals (a) to (c).
- **Oracle price in the journal (T3):** done. The `execute-swap` event carries `oracle-price`, `oracle-timestamp` and `min-out-floor`, the values the floor check used.
- **Units in the per-day cap (T3):** done. Each token has its own `max-per-trade`, `max-per-day` and window. A cap priced in a single unit needs the oracle above.
- **Stranded tokens (T4):** a way to recover tokens sent straight to the vault.
- **Approval band off-chain (T9):** done. The SDK predicts u126 to u133 (`checkIntent`, `checkRequest`, `checkApproval`), the MCP server builds the agent's request, the monitor raises `SWAP_REQUESTED` and `SWAP_REQUEST_EXPIRED`, and the dashboard shows the owner a pending request.
